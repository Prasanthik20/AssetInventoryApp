SYSTEM IMPLEMENTATION PLAN

Multi-Tenant Subscription Engine & Super Admin Control System Cockpit

Goal Description

Introduce an enterprise-grade Multi-Tenant Subscription and Billing System that automatically enforces usage limits (users, assets, storage) and validity dates. Accompanying this is a comprehensive Super Admin Control System allowing full tenancy lifecycle control, billing verification, plan adjustments, override features, and system auditability.

User Review Required

1. Tenant Isolation Method (Logical Sharing)

We recommend a Shared Database with Logical Isolation (tenantId column and application-level query enforcement). Since your Prisma schema and tables (Tenants, Users, Asset_Details, etc.) are already designed with tenantId fields, this is the most natural fit. However, for high-compliance enterprise clients, we recommend introducing a hybrid model where Enterprise plans can be routed to a Dedicated Database via dynamic connection pool switching in backend middleware.

2. Auto-Restricting Write Access on Over-Limit

When a limit is hit (e.g. Max Assets exceeded), all write API endpoints (POST, PUT, PATCH) for assets will throw a 403 Forbidden error with error code LIMIT_EXCEEDED, forcing the app to show a banner. Read operations (GET) will remain functional. A 7-Day Grace Period is configured by default post-expiry during which writes are permitted but alert overlays display at login.

3. Mobile Registration Verification

Registration must block access until an organization is registered. On mobile, we will enforce a check upon login: if the user does not have a tenantId linked, or if their Tenant is marked as PENDING_ONBOARDING, they will be redirected to an onboarding flow. This requires changes in both the API login endpoint and the Expo router.

4. Payment Processing Options

For Indian markets, Razorpay or Cashfree is standard. For international, Stripe. In order to launch quickly and scale securely, we support both automated PG integrations and a manual "Upload Bank Transfer Screenshot" workflow. Approvals are triggered instantly in the Super Admin Cockpit upon validation.

Core Architectural Accomplishments

  • Tenant Isolation Strategy: Logical database partitioning enforced through custom application-level Prisma filters. Additionally, raw database row-level security (RLS) is ready to configure using ALTER TABLE "Asset_Details" ENABLE ROW LEVEL SECURITY.
  • Dual-Database Portability: Out-of-the-box support for a cost-effective multi-tenant shared database for Starter/Pro tiers, alongside dynamic connection pool switching for routing Enterprise clients to secure, dedicated databases.

Subscription Lifecycle and State Machine

The tenant lifecycle operates under six standard states (Trialing, Active, Expired, Grace Period, Suspended, and Disabled). Banners adapt dynamically based on resource usage:

Figure 1.2: Resource Warning Banners and Hard Lockdown Tiers Dashboard Interface Flow

Usage Limit Warning Protocol

  • 70% Consumption: Non-intrusive dismissible cyan banner appears on the dashboard warning of incoming tier limits.
  • 90% Consumption: Persistent amber warning banner remains visible on all screens. Automail alert dispatched.
  • 100% Limit / Expired Expiration: Imminent lockdown. Disables database writes for assets, operators, and dynamic category extensions. Launches un-dismissible billing lock screen overlay.

// ==========================================
// Tenant & Subscription Schema Core
// ==========================================

model Tenants {
  id               String               @id @default(uuid())
  name             String
  organizationType String?
  institutionId    String?
  gstNumber        String?
  address          String?
  country          String?
  state            String?
  city             String?
  postalCode       String?
  status           String               @default("active") // "active", "expired", "suspended", "grace", "trialing", "disabled"
  createdAt        DateTime             @default(now())
  updatedAt        DateTime             @updatedAt

  users               Users[]
  subscriptions       Subscriptions[]
  Asset_Details       Asset_Details[]
  Category            Category[]
  Status              Status[]
  Asset_Assignments   Asset_Assignments[]
  Notifications       Notifications[]
  AssetCategoryFields AssetCategoryFields[]
  
  renewalRequests     RenewalRequests[]
  payments            Payments[]
  invoices            Invoices[]
  auditLogs           AuditLogs[]
  featureFlags        TenantFeatureFlags[]
}

model Plans {
  id        String   @id
  name      String
  maxUsers  Int
  maxAssets Int
  maxStorage BigInt   @default(2147483648) // 2GB
  price     Decimal  @db.Decimal(10, 2)
  currency  String   @default("INR")
  features  Json?    // Stores granular toggles (e.g. customCategories: true)
  createdAt DateTime @default(now())

  subscriptions Subscriptions[]
}

model Subscriptions {
  id                     String    @id @default(uuid())
  tenantId               String
  planId                 String
  startDate              DateTime  @default(now())
  endDate                DateTime?
  status                 String    @default("trialing") // "active", "expired", "past_due", "canceled"
  paymentProvider        String?   // "manual", "stripe", "razorpay"
  providerSubscriptionId String?
  createdAt              DateTime  @default(now())
  updatedAt              DateTime  @updatedAt

  tenant Tenants @relation(fields: [tenantId], references: [id])
  plan   Plans   @relation(fields: [planId], references: [id])

  @@index([tenantId])
}

model RenewalRequests {
  id             String    @id @default(uuid())
  tenantId       String
  planId         String
  requestedDate  DateTime  @default(now())
  transactionId  String    @unique
  paymentProofUrl String
  remarks        String?
  status         String    @default("submitted") // "submitted", "reviewing", "approved", "rejected"
  rejectionReason String?
  reviewedBy     String?   
  reviewedAt     DateTime?
  createdAt      DateTime  @default(now())
  updatedAt      DateTime  @updatedAt

  tenant Tenants @relation(fields: [tenantId], references: [id])
  
  @@index([tenantId])
  @@index([status])
}

model Payments {
  id            String   @id @default(uuid())
  tenantId      String
  amount        Decimal  @db.Decimal(10, 2)
  currency      String   @default("INR")
  status        String   @default("completed") // "pending", "completed"
  paymentMethod String   // "bank_transfer", "upi", "card"
  transactionId String   @unique
  paymentDate   DateTime @default(now())
  createdAt     DateTime @default(now())

  tenant Tenants @relation(fields: [tenantId], references: [id])
  
  @@index([tenantId])
}

High-Performance Relational Indexing Plan

To guarantee sub-millisecond query execution as tenant records scale, compound indexes are established on:

  • Asset_Details: Compound index on ("tenantId", "categoryId", "status_id") for instant dashboard categorizations.
  • Asset_Assignments: Compound index on ("tenantId", "operator_employeeId", "status") for lightning-fast operator lists.
  • AuditLogs: Compound index on ("tenantId", "createdAt") to process real-time admin audit logs.

Verification & Quality Assurance Plan

Automated Validation

Cross-Tenant Security Test: Integration script logs in with Tenant A's token, then attempts to view/modify Tenant B's equipment records. Expects 403 Forbidden or 404 Not Found.

Resource Overrun Test: Continuous scripting loops executing asset additions until limits are breached. Validates that the API halts writes and responds with LIMIT_EXCEEDED status code.

Manual Testing Flow

Super Admin registers a test tenant, logs in as that tenant and triggers an expired subscription scenario, validates the write lockdown, uploads a manual billing screenshot, returns to Super Admin dashboard to approve the receipt, and confirms that database access is instantly restored.
